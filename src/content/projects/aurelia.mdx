## Overview

Aurelia is a community management platform for Discord. It is usually described as "a bot", and the bot is what members see, but the product is larger: a Python service with modular command architecture, a web dashboard for configuration, public documentation, live statistics and a changelog.

I created it, built it and maintain it. It runs as an independent product with a live public dashboard.

## What it does

For community operators, Aurelia covers the recurring work of running a server:

- **moderation** with warnings tracked as numbered cases, escalating thresholds and a full audit log
- **onboarding** with configurable welcome cards in several formats and live preview
- **engagement** systems: leveling with role rewards, daily streaks, question of the day, giveaways with live entries, starboard and achievements
- **privacy controls**, including per-user data export and deletion commands

Every feature is configurable from the dashboard rather than requiring config file edits, which is the difference between a tool the owner can operate and one only its author can.

## System design

The bot is Python on discord.py, organized as cogs: focused modules that each own one concern, 47 of them at the current count. Commands resolve through 173 invokable paths, a number the project tracks and publishes rather than a marketing figure.

<Figure number="03" image={moderation} alt="Moderation surfaces: a numbered warning case, an AI automod nudge and audit log cards." caption="Moderation as numbered cases with a full audit trail." context="repository asset" />

The dashboard is a Next.js application with Discord OAuth, so server owners sign in with their Discord identity and only see servers they administrate. Configuration written in the dashboard reaches the bot through a shared data layer, and public surfaces like the stats page and documentation render from the same source of truth. Live statistics refresh continuously.

## AI architecture

Aurelia's conversational features run on a multi-provider design. Four providers, Gemini, Groq, Mistral and OpenRouter, sit behind a router that owns failover: adapters translate requests, and the router decides which provider answers and what happens when one is unavailable. Each adapter degrades cleanly when its key is missing, so a partial deployment boots without the unconfigured providers.

The design principle: no provider is special. Adding or removing one is a configuration change, not a rewrite, and no single outage takes the feature down.

## Lessons

Building a platform alone forces clarity about boundaries: the bot never reaches into dashboard concerns, providers never implement fallback logic, and every module can fail without taking the process down. The result is a codebase where features are added by writing a new cog, not by negotiating with existing ones.
